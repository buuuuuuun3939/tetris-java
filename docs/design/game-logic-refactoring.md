# ゲーム進行ロジックのリファクタリング設計

## 1. 目的

`GamePanel` に集まっているゲームルールと状態管理を画面処理から分離し、JUnitで個別に確認できる構造にする。画面の見た目やキー操作を変えず、段階的に移行する。

## 2. 現状の課題

現在の `GamePanel` は、次の責務を一つのクラスで扱っている。

- Swing画面の描画とキー入力
- Swing `Timer` の開始・停止と時間経過
- 現在位置、スコア、レベル、ゲーム状態、HOLD状態の保持
- 移動・回転・衝突判定・固定・ライン消去・スポーンなどのゲームルール
- BGMと効果音の再生

ゲーム状態は `private` フィールドにあり、主要なルールも `private` メソッドである。そのため、ルールを単独で呼び出したり、任意の盤面・ミノを用意して結果を確認したりしにくい。また、パネル生成時にタイマーとBGMが開始されるため、ゲームルールのテストにもSwingや音声の副作用が伴う。

## 3. 方針

- ゲームルールとゲーム状態を `Game` クラスにまとめる。
- `Game` はSwing、描画、キーイベント、タイマー、音声に依存させない。
- `GamePanel` は入力をゲーム操作に変換し、ゲーム状態を描画する。
- 位置はピクセルではなく盤面上の行・列で管理する。描画時に `Board.BLOCK_SIZE` を掛けてピクセルへ変換する。
- 既存の `Board`、`Tetromino`、`TetrominoBag` を利用し、最初の段階では不要なクラス分割を増やさない。
- ランダムなミノ生成を差し替えられる入口を用意し、ゲームテストでは順番を固定できるようにする。

## 4. クラス構成案

```text
Main
└── GamePanel
    ├── Game                 ゲーム状態とルール
    │   ├── Board
    │   ├── current piece / position
    │   ├── next piece
    │   ├── hold piece / hold-used flag
    │   ├── score / level / GameState
    │   └── TetrominoSource
    ├── Swing Timer           一定間隔で Game.tick() を呼ぶ
    ├── BgmPlayer             再生・停止
    └── SoundEffectPlayer     操作結果に応じた効果音
```

### `Game`

ゲームの状態を所有し、操作と時間経過を処理する。少なくとも次を担当する。

- 左右移動、ソフトドロップ、回転
- 移動・回転先の盤面境界と固定ブロックとの衝突判定
- 通常落下、ハードドロップ、ミノ固定
- 固定後のライン消去、スコア・レベル更新
- 次のミノの出現、出現可能性の判定、ゲームオーバー
- HOLDと1ミノにつき1回の制限
- ポーズ、再開、リスタート
- ゴースト位置の算出

ゲームルールの座標は盤面上のセル単位とする。たとえば現在位置を `currentRow` と `currentCol` で持ち、タイマー間隔やピクセル位置は `GamePanel` と切り分ける。

### `GamePanel`

- キーコードを `Game` の操作へ変換する。
- Swing `Timer` のイベントで `game.tick()` を呼び、再描画する。
- `Game` から取得した盤面・ミノ・スコア・レベル・状態を描画する。
- ポーズ状態やゲームオーバー状態の変化に合わせて、タイマーとBGMを開始・停止する。
- 操作の成否やゲーム結果に応じて効果音を再生する。

ゲームの状態を直接変更する処理や衝突判定を、`GamePanel` に戻さない。

### `TetrominoSource`（テスト用の差し替え口）

ゲームが次のミノを取得するための小さなインターフェースを設ける。

```java
interface TetrominoSource {
    Tetromino next();
}
```

本番用の実装は既存の `TetrominoBag` から種類を取り出して `Tetromino` を作る。テスト用の実装は、指定したミノを順番に返す。これにより「次にI型が出る」などの前提を固定でき、ランダム順に依存しないテストが書ける。

### ゲーム状態の読み取り

`GamePanel` が描画するために、`Game` から読み取り専用の状態を得られるようにする。初期段階では getter を使ってもよいが、可変配列をそのまま返さない。特に `Tetromino.getShape()` は内部配列を返すため、描画側が誤ってゲーム状態を書き換えないよう、防御的コピーまたは読み取り専用のスナップショットを使う。

状態の取得項目は、盤面、現在ミノと座標、次ミノ、HOLDミノ、スコア、レベル、ゲーム状態、ゴースト位置を想定する。必要が増えた段階で `GameSnapshot` のような不変データクラスにまとめる。初回から複雑なイベント基盤は導入しない。

## 5. 操作APIの案

以下は責務を示すための案であり、メソッド名や戻り値は実装時に既存コードと照合して決める。

```text
Game
├── moveLeft()                 操作の成否を返す
├── moveRight()                操作の成否を返す
├── moveDown()                 1セル下へ移動できたかを返す
├── rotate()                   回転できたかを返す
├── hardDrop()                 固定まで進め、結果を返す
├── hold()                     HOLDを処理する
├── tick()                     自然落下を1回進め、必要なら固定する
├── pause() / resume()          ゲーム状態を変更する
├── restart()                  初期状態へ戻す
└── 読み取り用メソッド         描画・判定に必要な状態を返す
```

操作の戻り値は `GamePanel` が効果音や再描画を判断するために使う。最初は `boolean` や小さな結果型で十分とし、イベントシステムは必要になってから検討する。

## 6. 既存処理の移動先

| 現在の処理 | 移動先・扱い |
|---|---|
| `canMoveLeft()` / `canMoveRight()` / `canMoveDownAt()` | `Game` の衝突判定 |
| `canRotate()` / `tryRotate()` | `Game` の回転処理 |
| `lockBlock()` / `landTetromino()` | `Game` の固定・着地処理 |
| `hardDrop()` | `Game` |
| `canSpawn()` / `spawnTetromino()` | `Game` |
| `hold()` | `Game` |
| `addScore()` / `updateLevel()` / `getDropInterval()` | スコア・レベル計算は `Game`。Swingタイマーの遅延反映は `GamePanel` |
| `togglePause()` / `restartGame()` | 状態初期化・切り替えは `Game`。Timer/BGMの操作は `GamePanel` |
| `getGhostY()` | `Game` のゴースト位置計算 |
| `draw*()` | `GamePanel` に残す |
| キーコード判定 | `GamePanel` に残し、対応する `Game` 操作を呼ぶ |

## 7. テスト方針

`Game` をJUnitから直接作成し、固定したミノ供給元を使って、操作前後の状態を比較する。Swingコンポーネントや実時間待機は使わない。

初期のテスト候補は次のとおり。

| 分類 | 主な確認内容 |
|---|---|
| 初期化 | 空の盤面、初期スコア・レベル、現在・次ミノ、初期位置 |
| 移動 | 左右・下への移動、壁・床・固定ブロックで移動できないこと |
| 回転 | 回転成功、壁際の補正、障害物で回転できない場合に状態が保たれること |
| 固定・落下 | 自然落下、ハードドロップ後の固定位置と盤面 |
| ライン・スコア | 1行・複数行の消去、スコアとレベルの更新 |
| 出現・ゲームオーバー | 次ミノの出現、出現位置が塞がれたときのゲームオーバー |
| HOLD | 初回HOLD、交換、ミノごとの1回制限、再出現位置への復帰 |
| 状態遷移 | ポーズ中の操作制限、再開、リスタート後の初期状態 |
| ゴースト | 固定ブロックや床までの最終位置 |

テスト対象はゲームルールに絞る。描画のピクセル単位の見た目、実際のキーイベント、音声デバイス、Swing Timerそのものは別の手動確認または結合確認の対象とする。

## 8. 段階的な移行手順

1. `Game` と `TetrominoSource` を追加し、初期化と読み取り用状態から作る。
2. `GamePanel` の盤面・ミノ・スコアなどの状態を `Game` に移し、描画は `Game` の状態を読むようにする。
3. 左右移動、下移動、回転を `Game` に移し、境界と障害物のテストを追加する。
4. 自然落下、固定、ハードドロップ、ライン消去、スコア・レベル更新を移し、テストする。
5. HOLD、スポーン、ゲームオーバー、リスタートを移し、状態遷移をテストする。
6. `GamePanel` に残った処理が入力変換・タイマー連携・描画・音声だけであることを確認する。
7. 既存の手動操作で、キー割り当て、表示、タイマー、音声の挙動を確認する。

各段階でアプリを動かし、従来の操作が保たれていることを確認する。大規模な一括移動は避ける。

## 9. 完了条件

- `Game` のゲームルールにSwing、Graphics、Timer、音声プレイヤーへの依存がない。
- ゲームルールのテストが固定ミノ順で決定的に実行できる。
- `GamePanel` がゲーム状態を独自に重複保持せず、`Game` を通じて読み書きする。
- 移動、回転、固定、ライン消去、スコア、HOLD、ポーズ、ゲームオーバーをテストで確認できる。
- 画面表示、キー操作、タイマー、音声の手動確認で既存の基本動作が維持されている。

## 10. 今回の設計に含めないもの

- 描画コードの全面的な作り直し
- ネットワーク対戦や通信プロトコル
- 高度なイベントバス、DIフレームワーク、ゲームエンジンの導入
- スコア計算専用クラスなど、必要性がまだ明確でない細分化
- macOSアプリ化や配布方式の変更
